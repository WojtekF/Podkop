# Contract events leave a slice through a transactional outbox

A slice announces its contract events by writing them to an `outbox_messages` table **inside the same transaction as the state change that caused them**, and a background processor publishes them afterwards — rather than publishing in-process straight after `SaveChangesAsync` returns, as `EfUnitOfWork` does today. The current arrangement has a real loss window: `Features/FindingComments/Podkop.FindingComments.Infrastructure/EfUnitOfWork.cs` commits the comment and *then* publishes `CommentPosted`, so a crash between the two durably persists a comment whose announcement no consumer ever hears — Findings' comment count silently drifts from the truth, with no retry and no trace. One commit cannot span the two effects while the announcement lives outside the database. Writing the announcement as a row makes it part of the same commit, which is the only place atomicity is available to us. Decided in [#94](https://github.com/WojtekF/Podkop/issues/94); enabled by the shared kernel's generic `IDomainEvent` and `AggregateRoot` ([ADR 0013](0013-shared-domain-kernel.md)), without which one interceptor could not drain every slice's aggregates.

## Consequences

- **Delivery becomes asynchronous and at-least-once, and this is the substantive change.** Today `CommentPosted` is handled before the posting request returns, so the comment count is correct the instant the caller sees a 201. Once the processor owns delivery, the announcement lands *after* the commit — by milliseconds normally, by longer under load or after a restart — and may land **more than once**, because a processor that publishes and then dies before marking the row processed will publish it again. Both are accepted, not incidental.
- **Consumers must be idempotent, and are not yet.** `Findings.CommentPostedHandler` calls `IncrementCommentCount()` unconditionally; under redelivery it double-counts. Every contract-event handler needs a way to recognise an event it has already applied — the per-slice inbox table this issue's later slice adds. No consumer may be pointed at the processor before that exists.
- **Reads are eventually consistent across slices.** A just-posted comment may briefly not be counted on its finding. This is the same consistency ADR 0010 already accepted between schemas; the outbox makes the window explicit and bounded by the processor's poll rather than pretending it is zero.
- **The outbox row carries the public contract event, not the domain event.** Translation from domain event to contract event happens at save time, in the producing slice, through an `IContractEventTranslator` the slice registers; the row stores the contract type's name and its JSON. The processor therefore needs no knowledge of any slice — it resolves the type, deserializes, and publishes. The alternative, storing the domain event and translating at publish time, was rejected on two counts: it pushes per-slice knowledge into the shared processor, and it makes a slice-internal type part of a durable on-disk format, so renaming `CommentAdded` would break stored rows. Contract events are already the slice's public, primitive-only vocabulary (ADR 0003), which is exactly what a durable wire format wants.
- **Each slice's outbox lives in that slice's own schema** (ADR 0010) — `finding_comments.outbox_messages`, never a database-wide shared table. A shared table would be a cross-slice write dependency and a single migration every slice contends on. The cost is one identical table definition per converted slice, applied from one shared model-builder extension.
- **`Podkop.Shared.Infrastructure` gains EF Core and stops being semantically weightless.** It holds the interceptor, the `OutboxMessage` row, and the table's model configuration. ADR 0013 rules `Podkop.Shared.Domain` out of this — the kernel references nothing, and an interceptor is EF Core code by nature. Extending the existing shared infrastructure project was chosen over a new one; it previously held only sample-data vocabulary, and now also holds the one messaging mechanism every slice shares. Keeping MediatR out of it is deliberate: the translator returns `object?`, so the shared project depends on no message bus and the choice of one stays replaceable.
- **The mechanism is only worth its weight where a contract event crosses a slice boundary.** A slice raising domain events nobody outside consumes has nothing to translate and needs no outbox. Adoption is per slice and by evidence, starting with FindingComments — the slice that has both the cross-slice event and the loss window.
