# Contract events leave a slice through a transactional outbox

A slice announces its contract events by writing them to an `outbox_messages` table **inside the same transaction as the state change that caused them**, and a background processor publishes them afterwards — rather than publishing in-process straight after `SaveChangesAsync` returns, as `EfUnitOfWork` does today. The current arrangement has a real loss window: `Features/FindingComments/Podkop.FindingComments.Infrastructure/EfUnitOfWork.cs` commits the comment and *then* publishes `CommentPosted`, so a crash between the two durably persists a comment whose announcement no consumer ever hears — Findings' comment count silently drifts from the truth, with no retry and no trace. One commit cannot span the two effects while the announcement lives outside the database. Writing the announcement as a row makes it part of the same commit, which is the only place atomicity is available to us. Decided in [#94](https://github.com/WojtekF/Podkop/issues/94); enabled by the shared kernel's generic `IDomainEvent` and `AggregateRoot` ([ADR 0013](0013-shared-domain-kernel.md)), without which one interceptor could not drain every slice's aggregates.

## Consequences

- **Delivery becomes asynchronous and at-least-once, and this is the substantive change.** Today `CommentPosted` is handled before the posting request returns, so the comment count is correct the instant the caller sees a 201. Once the processor owns delivery, the announcement lands *after* the commit — by milliseconds normally, by longer under load or after a restart — and may land **more than once**, because a processor that publishes and then dies before marking the row processed will publish it again. Both are accepted, not incidental.
- **Consumers must be idempotent, and are not yet.** `Findings.CommentPostedHandler` calls `IncrementCommentCount()` unconditionally; under redelivery it double-counts. Every contract-event handler needs a way to recognise an event it has already applied — the per-slice inbox table this issue's later slice adds. No consumer may be pointed at the processor before that exists.
- **Reads are eventually consistent across slices.** A just-posted comment may briefly not be counted on its finding. This is the same consistency ADR 0010 already accepted between schemas; the outbox makes the window explicit and bounded by the processor's poll rather than pretending it is zero.
- **The outbox row carries the public contract event, not the domain event.** Translation from domain event to contract event happens at save time, in the producing slice, through an `IContractEventTranslator` the slice constructs and hands to its own interceptor (see the amendment below); the row stores the contract type's name and its JSON. The processor therefore needs no knowledge of any slice — it resolves the type, deserializes, and publishes. The alternative, storing the domain event and translating at publish time, was rejected on two counts: it pushes per-slice knowledge into the shared processor, and it makes a slice-internal type part of a durable on-disk format, so renaming `CommentAdded` would break stored rows. Contract events are already the slice's public, primitive-only vocabulary (ADR 0003), which is exactly what a durable wire format wants.
- **Each slice's outbox lives in that slice's own schema** (ADR 0010) — `finding_comments.outbox_messages`, never a database-wide shared table. A shared table would be a cross-slice write dependency and a single migration every slice contends on. The cost is one identical table definition per converted slice, applied from one shared model-builder extension.
- **`Podkop.Shared.Infrastructure` gains EF Core and stops being semantically weightless.** It holds the interceptor, the `OutboxMessage` row, and the table's model configuration. ADR 0013 rules `Podkop.Shared.Domain` out of this — the kernel references nothing, and an interceptor is EF Core code by nature. Extending the existing shared infrastructure project was chosen over a new one; it previously held only sample-data vocabulary, and now also holds the one messaging mechanism every slice shares. Keeping MediatR out of it is deliberate: the translator returns `object?`, so the shared project depends on no message bus and the choice of one stays replaceable.
- **The mechanism is only worth its weight where a contract event crosses a slice boundary.** A slice raising domain events nobody outside consumes has nothing to translate and needs no outbox. Adoption is per slice and by evidence, starting with FindingComments — the slice that has both the cross-slice event and the loss window.

## Amendment: how a slice joins the outbox

The decision above said a producing slice supplies its translator "through an `IContractEventTranslator` the slice registers", and `AddFindingCommentsPersistence` duly registered one as a singleton. That held while FindingComments was the only slice announcing anything, and stops holding at the second: [#77](https://github.com/WojtekF/Podkop/issues/77) makes Findings announce the tag namespace's pair, and the Microblog slice ([#74](https://github.com/WojtekF/Podkop/issues/74)) is specced to be a third. Two slices registering the same singular service means the last registration wins and one slice's announcements vanish — no error, no failing test, just an index that stops hearing about changes. This amendment says how a slice joins the outbox, rather than leaving it to whichever registration ran last. Decided in [#104](https://github.com/WojtekF/Podkop/issues/104).

- **The bug was cardinality, not dependency injection.** A *one-per-system* service registered by *N* slices collides; the container has no way to know that two answers to `IContractEventTranslator` were meant for different contexts, so it keeps the last one. The additive `IEnumerable<T>` registration is the collision-free dual of the same mechanism — N slices each contribute one, and the consumer receives all of them. Both shapes appear below, and which one a given seam wants is decided by whether the system needs one of the thing or all of them. This is the general rule the rest of these bullets apply; it is not specific to the outbox.
- **A slice constructs its own translator and hands it to its own interceptor; nothing registers one in the container.** The interceptor keeps its `(translator, timeProvider)` constructor, but `IContractEventTranslator` stops being a DI key — it survives only as the type the constructor is declared against. DI resolution was buying nothing here: every translator is `sealed`, parameterless, and stateless, there is exactly one correct instance per `DbContext` known at compile time inside the slice's own Infrastructure project, and nothing substitutes one — the write-side specs construct theirs directly. What it cost was a shared name for two slices to collide on. A translator that later needs a dependency does not reopen this: the slice's `AddXPersistence` already has the service provider in hand and passes `TimeProvider` through the same way. The failure mode is deleted rather than guarded, which is why the shapes that guard it — keyed registration per slice, a generic `OutboxSaveChangesInterceptor<TTranslator>`, an `AddSliceOutbox<TContext, TTranslator>()` helper owning the wiring — were all rejected: each is machinery for making DI-resolved translation safe, and there is no DI-resolved translation left to make safe.
- **A slice declares that it produces by putting the outbox table in its model.** `modelBuilder.AddOutboxMessages()` is the authoritative fact, because it is the one that cannot lie: no call means no table, no migration, and rows that physically cannot be written. A marker interface on the context or an entry in a roster can each claim "producer" while the table is absent, and so add a way for two declarations to disagree rather than removing one. Reading the declaration back — the built model contains `OutboxMessage` — names only shared types, so the composition root learns that a context produces without learning which slice it belongs to (ADR 0003). The cost is that the declaration is made in a model file and read somewhere else, so it is not visible at the registration call site; the guard below is what keeps that from mattering.
- **The outboxes a delivery pass drains compose rather than being listed.** Each producing slice registers its own drain from its own `AddXPersistence`, and `OutboxProcessingService` resolves the set. The hand-maintained `ProducingOutboxes` — "the one list that has to grow when a slice starts producing" — goes away, and with it a second silent failure: a slice that wrote rows nobody drained accumulated them with `ProcessedAt` null forever. Registering the drain beside the interceptor attachment puts the two steps that must move together in one method instead of two projects. Deriving the set instead — scanning registered context types and draining every one whose model carries an outbox — would be strictly unforgettable and was still rejected: it overturns this ADR's "explicit rather than scanned" position for the type registry, and it removes the one place in a diff where a reviewer sees a new producer join the system. If that trade is ever worth making it deserves its own amendment.
- **Forgetting the wiring fails at review rather than in production silence.** "This slice produces nothing" and "this slice forgot to wire up" are the same observation unless something independently asserts the slice is a producer, which is what the model declaration provides. A helper in `Podkop.Shared.Testing` walks a built host's registered contexts, keeps those declaring an outbox, and asserts each carries the interceptor and has a drain. It is written as an enumeration rather than a list, so a slice that starts producing is covered the day it declares an outbox — a guard that itself has to be extended per slice would only be a fourth roster. The two assertions have different scopes: `Podkop.MigrationService` registers the same contexts and so must carry the interceptor, but runs no delivery loop and so is not required to drain. `Podkop.Shared.Testing` is the right home under ADR 0013, which already classes it as a convenience with no semantic weight; the drain registration joins the outbox machinery this ADR already put in `Podkop.Shared.Infrastructure`. Nothing here enters `Podkop.Shared.Domain`, so the kernel's admission test is not engaged at all.
- **`ContractEventTypeRegistry` is deliberately left as it is.** It looks like a third hand-maintained per-slice roster and is not one: the other two record wiring a slice knows about itself, while the registry is an allowlist deciding what the processor may resurrect from disk, and an allowlist that populates itself is not an allowlist. It also could not be replaced by a scan even if that were wanted, because nothing can enumerate contract events: ADR 0013 keeps `Podkop.*.Contracts` kernel-free precisely so contract events carry no shared marker, and those projects hold more than events — `Podkop.Tags.Contracts` also holds the `Tag` value type and the `TaggedContentTypes` constants. The hand-written roster is the only enumeration of contract events that exists. What is genuinely wrong with it is where its failure lands: a name resolving to nothing has the exception recorded in the row's `Error` column, the row parks after `MaxAttempts`, and nobody reads either. Making parked rows observable is a separate concern from producer wiring and is tracked on its own.
- **The operational recipe lives with the scaffolding rules, not here.** This record is read by someone asking why the outbox is shaped this way; the wiring is got wrong by someone asking how to add a producer. `docs/agents/scaffolding.md` is the document a scaffolding session must read before scaffolding, so the steps for wiring a producing slice belong there, and this ADR keeps the reasoning.
