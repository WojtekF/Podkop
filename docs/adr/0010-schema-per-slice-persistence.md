# Schema-per-slice persistence with EF Core and PostgreSQL

Podkop's slices move from in-memory stores to a single Aspire-orchestrated PostgreSQL database with **one schema per slice**: each slice owns a `DbContext` in its existing Infrastructure project, with its own migrations and its own `__EFMigrationsHistory` table inside its schema. This is the lowest-cost isolation level that keeps ADR 0003's slice boundaries real at the data layer — a shared DbContext would require a persistence project every slice references, and database-per-slice buys operational cost the prototype doesn't need. Decided while resolving [Persistence decisions](https://github.com/WojtekF/Podkop/issues/57); options, sources, and version evidence in [docs/research/persistence-patterns-efcore-postgres.md](../research/persistence-patterns-efcore-postgres.md).

## Consequences

- Schemas are the slice name in snake_case (`findings`, `finding_comments`, `documents`, `users`, `moderation`); tables and columns are snake_case too, via the EFCore.NamingConventions package.
- **No cross-schema foreign keys.** Cross-slice references stay plain ID columns; referential integrity remains at the application/Contracts level, and each slice's migration stream stays independent. Cross-slice writes are **eventually consistent** via contract events — no cross-context transactions. (One shared database keeps `Database.UseTransaction` on a shared connection available as a future, explicitly-reviewed exception if a hard invariant ever demands it.)
- Migrations are applied by a dedicated `Podkop.MigrationService` worker — the stable Aspire pattern — which references every slice's Infrastructure project (a sanctioned isolation exception, like `Podkop.Server` is for Server projects), migrates each context in sequence, then runs the Development-gated demo seed: the existing per-slice sample generators, invoked idempotently. Aspire's `AddEFMigrations` replaces the worker once its package leaves prerelease.
- Endpoint tests run against real PostgreSQL via Testcontainers with Respawn resets, through a fixture in a new test-only `Shared/Podkop.Shared.Testing` project — Docker becomes a hard requirement for dev machines and CI. EF InMemory and SQLite were rejected: Microsoft discourages the former, and the latter cannot express schemas at all.
- Column mapping follows Npgsql defaults (`uuid` keys, `timestamptz` timestamps, un-capped `text`) with one deviation: enums are stored as text via `HasConversion<string>`, keeping values readable in psql and immune to enum reordering.
- Conversion order: foundation + Users first (smallest slice proves the pipeline end-to-end, and the auth epic needs real users), then Findings, then FindingComments, then Moderation (its seeds reference both); Documents is independent and can convert any time after the foundation.
