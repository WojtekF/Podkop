# Authentication is ASP.NET Core Identity with cookie sessions, served one-origin

Podkop authenticates with ASP.NET Core Identity backed by EF Core stores inside the Users slice's `users` schema — one `PodkopUser : IdentityUser<Guid>` row per user, carrying the slice's `Role` column, with the domain `User` projected from it. Sessions are the Identity application cookie (HttpOnly, Secure, SameSite=Lax, sliding), BFF-style: no token ever reaches the browser, and CSRF is covered by antiforgery using Angular's `XSRF-TOKEN` pattern. The auth endpoints are hand-rolled minimal APIs over `UserManager`/`SignInManager`, because `MapIdentityApi` is email-only and shape-fixed while Podkop identity is username-first like Wykop's. The SPA is same-origin with the API everywhere — Angular's dev-server proxy in development, the production build served by `Podkop.Server` in deployment — so cookies and XSRF behave identically in both and CORS never exists. `users.Role` stays the single source of truth for roles: sign-in projects it into a role claim, and no Identity role tables are used.

## Considered Options

- **Keycloak via Aspire** — hosted login UI and standards-compliant OIDC, but the Aspire integration is preview-status, every dev loop gains a container plus realm bootstrap, PII splits across two stores (two GDPR surfaces for ADR 0007's erasure), and Podkop's own promotion feature would mutate roles through the Keycloak Admin API instead of a row the slice owns. The honest fork if multi-client SSO becomes near-term; nothing in today's Podkop pays for it.
- **Tokens in the browser** (the `MapIdentityApi` bearer scheme or self-signed JWTs) — recommended against by Microsoft for browser clients and by OWASP (any XSS steals storage-held tokens), which weighs double on a user-generated-content site. OpenIddict can layer standards-based tokens onto the same Identity store later if mobile or third-party API access arrives, so choosing cookies now forecloses nothing.
- **Identity's role store** (`AspNetRoles`/`AspNetUserRoles`) — conventional, but it would duplicate the `users.Role` fact into framework tables that product features (moderator promotion, the future Administrator) must keep in sync with the slice's own state.
